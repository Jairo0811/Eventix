# Eventix v1.4.0 — Fases 3 y 4: pagos e infraestructura

> **Estado: preparación técnica, NO lanzamiento comercial.** Última release
> formal verificada: v1.3.4. No se ha creado una pasarela bancaria certificada,
> un webhook público ni un servidor productivo en esta fase.

## Fase 3 — Preparación de pagos comerciales

### Protecciones implementadas

1. `SimulatedPaymentGateway` no se registra bajo el perfil Spring `prod`
   (`@Profile("!prod")`). CARDNET, Azul tradicional, Qik, Stripe, PayPal y
   transferencia **no heredan una aprobación simulada en producción**.
2. `EVENTIX_CHECKOUT_ENABLED=false` por defecto en `application-prod.yml`
   y `render.production.yaml`. Las compras del comprador y las ventas/cobros
   administrativos se rechazan en backend antes de mutar datos.
3. El checkout muestra un aviso y deshabilita su botón cuando la función
   está cerrada; el servidor sigue siendo la autoridad, incluso ante POST
   fabricados. En `dev`/CI el flujo de simulación se conserva.
4. `ProductionReadinessValidator` se activa exclusivamente con `prod`:
   exige URL pública HTTPS, SQL Server con `encrypt=true` y
   `trustServerCertificate=false`, credenciales diferenciadas de app/Flyway,
   secreto HMAC, claves de firma persistentes y bootstrap inseguro desactivado.
   Nunca imprime valores de secretos.
5. La migración Flyway `V35__create_verified_payment_webhook_inbox.sql`
   prepara un **inbox de eventos verificados**, con índice único por
   `(provider, external_event_id)`. Guarda un hash SHA-256, referencia,
   proveedor, fecha y estado; **no** guarda PAN, CVC, tokens ni el cuerpo íntegro.
   El servicio de registro no procesa pagos ni emite entradas.

### Lo que NO está habilitado

- No hay endpoint de webhooks bancarios. No debe crearse uno que acepte
  `status=APPROVED` del solicitante como prueba de pago.
- No se ha implementado la verificación del esquema oficial de firma, sello
  temporal, ventana anti-replay o verificación de la referencia bancaria por API.
- No hay reconciliación real, manejo completo de chargebacks/disputas,
  conciliación con movimientos externos ni payouts bancarios automáticos.
- El adaptador Azul para wallets existente no supone que Eventix tenga
  credenciales autorizadas, validación de sandbox ni licencia de comercio.
- El inbox evita duplicados con una restricción única en la base de datos.
  La verificación criptográfica debe efectuarse **antes** de llamar a
  `VerifiedWebhookInboxService`. Aun con el inbox, cada evento debe vincularse
  con la referencia interna, importe exacto, moneda y estado de la venta bajo
  una transacción idempotente; eso es un bloque posterior.

### Activación futura del checkout

La bandera `EVENTIX_CHECKOUT_ENABLED` **no es un interruptor para demostrar
pagos reales**. Permanece en `false` hasta que se complete:

- Contrato oficial del adquirente y credenciales concedidas formalmente.
- Certificación del flujo de prueba y autorización del comercio.
- Verificación de firmas de webhooks, idempotencia, reintentos, conciliación y
  reembolsos, con tests de rechazo/suplantación/replay.
- Inspección de seguridad, registros sanitizados, trazabilidad, monitoreo y
  evaluación del cumplimiento aplicable a tarjetas.
- Aprobación de lanzamiento y rollback operacional.

La validación startup actual exige `AZUL_WALLET_ENABLED=true`, ambiente
`PRODUCTION` y secretos requeridos si alguien intenta activar checkout
en `prod`. Esta validación **no certifica** un proveedor, ni sustituye los
puntos anteriores. Solo evita una activación accidental manifiestamente
incompleta.

## Fase 4 — Infraestructura comercial preparada

### Configuraciones

- `render.yaml`: demo H2 temporal, sin pagos reales. No modificar ni
  conectarla a bases de producción.
- `render.production.yaml`: blueprint **opcional**, de pago, con
  `SPRING_PROFILES_ACTIVE=prod`, despliegue automático apagado, healthcheck,
  directorio de portadas persistente, variables confidenciales `sync:false`,
  `EVENTIX_CHECKOUT_ENABLED=false`, wallets externos apagados.
- Base: SQL Server externo **con licencia apta para producción**, persistencia,
  backups, TLS con certificado verificable, usuarios distintos para aplicación
  y migraciones Flyway. No utilizar SQL Server Developer Edition para venta.
- Key material: Ed25519 y HMAC estables, gestionados y respaldados externamente.
- Dominio público HTTPS propio y URL `APP_BASE_URL` consistente.
- Netlify se mantiene como demo informativa, no como origen de sesiones.

### Procedimiento de salida controlada

1. **No desplegar todavía.** Confirmar plan/hosting y presupuesto con el
   propietario. Guardar secretos fuera de GitHub, logs y artefactos.
2. Crear **SQL Server externo** licenciado y red segura con TLS.
   Aplicar primero V35 en una **copia restaurada** y comprobar la integridad.
3. Configurar las variables privadas exigidas por `ProductionReadinessValidator`.
   No usar `trustServerCertificate=true`, perfiles `dev` ni el administrador demo.
4. Desplegar la infraestructura aprobada como staging **sin** permitir
   checkout. Verificar `/actuator/health/readiness`, autenticación y roles,
   eventos, archivos persistentes, logs y métricas.
5. Reiniciar y comprobar persistencia de BD, firmas y portadas.
6. Probar backup/restore en entorno separado; documentar RPO/RTO, monitoreo,
   auditoría y procedimiento de incidentes.
7. Ejecutar pruebas de accesibilidad, E2E, concurrencia y límites por rol.
8. Completar la integración bancaria real en una rama posterior, sin
   cambiar la demo gratuita. Activación solo después del visto bueno comercial.

## Comprobaciones de CI

- `ProductionReadinessValidatorTest`: configuración segura e insegura, checkout
  cerrado, límites para apertura con Azul Wallet, perfiles.
- `CustomerCheckoutServiceTest` y `DefaultSaleServiceTest`: guardias de backend
  antes de repositorios o gateways.
- `VerifiedWebhookInboxServiceTest`: hash, validación de entrada y duplicados.
- Docker + SQL Server en GitHub Actions valida Flyway V35 junto al resto de
  migraciones y el mapeo JPA.
- El CI verde prueba integridad técnica del código; **no** implica que Render
  producción esté desplegado ni que un banco haya autorizado cobros.

Esta preparación no elimina la necesidad de un diseño formal de idempotencia
de cargos y reembolsos externos, webhooks firmados, conciliación y event outbox.
